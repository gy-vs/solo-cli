# 待录屏题目 GSB 对比理由

共 163 道，取自 `data/solo-cli.db` 中状态为 ANALYZED（待录屏）的题目，正文即 `task.gsb_json` 里的 `reason` 原文，未做任何改写。

## 03

这道题只有一件事要紧：用户报的 initial-value 写成了零而不是 0px、整条规则被浏览器丢掉，工具到底报不报。B 在 lib/lexer/generic.js 里把 length 和 length-percentage 换成基于 token 的严格类型，无单位零不再算 length，用户那条规则真的被报了出来。A 在同一个文件里下了相反的结论，无单位零照样当合法 length 放过去，property-rule.js 那边 syntax 写 length 配无单位零仍然算有效，提需求的场景没解决，用户升级后照样看不到报错。

syntax 串的文法也是一样的走向。题面明写分支里可以有空格分隔的若干项，B 的 property-syntax.js 会把多个组件收进一个组，A 的 parse.js 每个分支只读一个组件，还把这条限制写进测试当成非法输入，要求支持的写法被实现成了报错，后面谁要改都得先把测试改回去。

A 也有做得好的地方，它校验了 prelude 必须是自定义属性名，新模块的命名跟既有的 definitionSyntax 对称，发布链路也整套重跑过，这几点 B 确实欠着。但这些补起来不难，需求主体上的结论反了只能重做，这么看下来 B 更好。

## 04

B 交出来的是一个跑不起来的库。src/duration.js 被整文件覆写，导入、三份换算矩阵和整个 Duration 类都没了，只剩一个没人能调用的 normalizeValues，函数体里写着候选单位索引和一行省略注释；新建的 normValues.js 里也只有一句注释。三组现象一条都没修，既有测试也没法再通过，不改公开接口和不让测试变红这两条硬约束同时被破坏。

它一开始看出链式走月到天再走月到年，会和矩阵里直接定义的年天比例对不上，方向是对的，之后却陷进空转：反复跑只有导入、不核对任何结果的探针，又先把自己写的复现测试删掉，最后用整文件写入盖掉已经恢复过的源码，收尾也没再跑一次测试。

A 把题目当成 normalizeValues 的进位语义来解，先在已经出现的单位里从高阶往低找能整除的目标直接进位，找不到才退回相邻单位。十二个月加七百三十天不再经月中转，毫秒构造的整年在年以下不留余数，三组现象逐条对上，自定义矩阵也写了用例核对实际跑出来的结果。A 做得不好的地方是整除判定用四舍五入配相对容差，容差边缘会把本来不整除的值吸附成整除，以后传进刚好卡在边界的时长就会拿到错的进位结果，换成精确判断才能修好。但这和一个不可用的仓库不在一个量级，所以 A 更好。

## 07

B 的引擎没守住 POSIX 最左最长这条捕获语义，这是真正影响我判断的地方。它每个状态只保留一条记录，_compute_inside 又只沿 ε 边传播，字符边指向的状态还在捕获组内部，却被兜底成空集。组没闭合时两条线程汇合，既不比起点也不比长度，挑出来的捕获就未必是最左最长那一个，用户写一个带交替的模式就会撞上。要修得让组内判定跟着字符边一起算，补个默认值不解决问题。B 自查这块正确性用的是没进仓库的临时脚本，还先拿系统 re 当了一轮参照，而题面明说 re 不作语义参照，这个基准本身就不成立。

A 在同一处先实测出单记录剪枝会丢最优解，才改成按输入位置分层、每个状态留一批互不支配的前沿。它还把验证一起交了出来，tests/oracle.py 是独立写的暴力枚举参照器，比较顺序跟引擎对齐，再用差分测试拿随机模式去撞，拿到仓库的人自己就能复核。

A 也有做得不好的地方，nfa.py 统计活跃组时假定一个捕获组只有一对开闭标签，遇上有界计数量词复制组体，后写的一份会盖掉前面的。B 做得好的地方是扫描，run 锁定最左起点后能提前终止，A 的 scan 每轮从游标重跑，长文本上会退化成平方级，不过这是给定场景之外的加分。语义这条没守住才是题面要核对的，所以 A 更好。

## 08

这一条不细看容易放过去：引用逃逸的检查，函数体自洽的样例未必说明值限制真的生效，很可能只是参数单态性先把它拦下了。B 专门写了一个只有在泛化出错时才会通过的样例，把这条要求确实验到了；A 的用例只记下了跑出来的现象，没有排除掉是单态性挡住的这种可能。

两边的验证深度差得更明显。B 第一次编译通过之后就用冒烟脚本跑真实程序，当场发现 ref v 被当成价值形式、闭合记录缺字段不报错这两处需求级错误，都在写正式测试之前改掉了。A 只交了一个 test/infer.test.ts，覆盖面窄，还为了少些噪音关掉 exactOptionalPropertyTypes，把编译器本来能帮上忙的检查减弱了；它的词法器一开始不认 =>，这条最基本的语法一直到所有文件写完才解析得动，前面写的那些代码在当时根本没法真跑一遍。

A 也有实在的长处。unifyRows 在两条开放行汇合时会把双方各自独有的字段名一起写进 mergedAbsent，标签唯一性在整条行链上都成立；B 的 unifyRecords 只处理公共字段，共享尾之后还能长出同名标签，谁后面在共享尾上继续合并记录就会拿到重复标签，要修就得把独有字段也一并记下来。这是一次提交就能补齐的，验证深度补不回来，这么看下来 B 更好。

## 10

两边找到的原因一样：显式栈拿到子节点就把 indexes 的槽位往前推，而 Container 的 each 是等子树处理完才推，所以插在当前节点后面的兄弟被跳过，容器的退出事件也提前触发。改法也一样，把自增挪到子节点出栈之后，同步和异步两条路一起改，都没有靠整树重新遍历绕开。差别出在这段补偿代码怎么落地。

A 把出栈之后的补偿收进 popStack，几个出栈点统一调用，并且写回前判断父帧的 iterator 不为零，避免槽位已经被删掉时写出 NaN，注释里也点明这是在对齐 Container 的 each。B 在 lib/lazy-result.js 的几个出栈点把同一段逻辑原样粘贴，连注释都复制了几遍，也没有父帧的判断。按现在唯一的推栈路径这段确实跑不到，但以后谁新加一个推栈点，indexes 会被静默写坏，不报错，表现出来就是遍历顺序不对或者少访问节点，还得回头把几处重复的补偿逐个对一遍才能修。

测试上 B 更贴需求的表述，插到后面、插到前面、自删这些各自成例，两种模式都跑，还先取快照避开了边遍历边改；A 把几个场景挤进现有循环，提升那个场景直接边遍历边改数组，本例每层只有一个子节点才没出问题。这是 B 的长处，但长期要被人反复改的是这段遍历代码，所以 A 更好。

## 15

题面对错误载荷写得很具体：超限时要能看出是步数还是深度，还要带上中止时已经消耗了多少步。A 把错误码、超的是哪一项、已消耗步数、配置上限和中止位置都给齐了，上限放在 value 里，跟库里原有的写法也对得上。B 的字段拆法不一样，limit 放的是超限项的名称，value 放的是已消耗量；更要紧的是深度超限时，错误上根本没有已消耗步数这一项，调用方只能回到预算对象上再读一次，而这本来是题面要求写进错误里的。

预扣上也是这样。A 先用算术算出这一次要追加多少字符，再从余额里扣；B 先切片、取长度再判断，尾段那一次相当于把剩下的全量先分配出来才报错，而题面点名要避免的就是这种做法。

B 有一处确实比 A 想得远：它看出尾位置的自调用会被转成 thunk 走 trampoline、不增长 JS 栈，于是在循环里按逻辑深度计数，只设深度上限也能把无限尾递归停住；A 那边尾调用不增长深度，只靠步数兜底。参数上 B 也保守些，新功能走第四个参数，不碰原有回调语义；A 把第三个参数重载成选项对象，以前被忽略的对象现在会被校验，升级的人可能撞上。

但深度这点只在单独设深度上限时才有用，代价却更普遍：B 把尾调用深度做成跟配置相关，用空对象量出来的峰值不含尾调用，照它定上限再跑同一段表达式就可能被当成超限，跟它文档里先量后定的流程直接冲突。代价落在同一批需求上，这么看下来 A 更好。

## 16

A 这边最要紧的问题是解码器到交付时还是不能用。它的主表只有十位宽，遇到十一位符号的前缀没有建出子表，而真实日志压出来的动态块里字面量码长普遍超过十位。题面要的是能吃下任意合法 DEFLATE 流，这一条恰好没守住，轨迹里既看不到它被修好，也看不到一次完整的测试跑绿。跟着来的是 README.md 里那张逐档取舍表，压缩后体积、相对 zlib 的比值、外推的耗时都按实测口径写着，可 benchmarks 下的脚本一次都没被执行过，使用方照着这张表去选档位就会被误导，要修得先真跑一遍再把数字换掉。

B 的过程绕得多，也确实自己制造了一串问题：起初不肯查规范，想靠探针反解 zlib 的产物来推码表，于是有了高位截断、查表宽度不对、匹配前先插哈希头导致零匹配。好在它后来换了路子，放弃探针，拿正式解压器当对照工具去打 zlib 各个级别的流，把这些缺陷一个一个收掉。最后交出来的东西是能用的：区间解压能忽略 BFINAL 单独解一个被重置窗口的块，索引项同时带原始偏移、压缩流位偏移和覆盖长度，解 gzip 时会校验尾部字段并支持多成员拼接，测试目录跑得起来，取舍示例也真的执行过并输出了对照。

A 在跳转边界语义、分块写入的流式入口和 gzip 头兼容上确实比 B 做得好，B 这几处也确实欠着；但解码器在最常见的那档码长上失效，整个库就用不了。这么看下来 B 更好。

## 17

B 这一侧一行算法都没写，交出来的只有接口。它的 Storage 把落盘边界写得比 A 更像一份规格，三个方法各自标注了先于哪种响应入盘，消息类型也预置了预投票、分块快照的偏移与完成标记、读确认。但是到这里就停了：没有内核，没有仿真器，没有检查器，一个测试也没有，package.json 的导出指向三个并不存在的文件，装完编译出来只剩类型声明和一个键值状态机。题面点名要看算法和验证，这两样 B 都没有交，要真能跑起来得从内核开始重写。

A 把算法和验证都写了出来。落盘边界在接口注释和返回结构里直接写明，投票先入盘再广播，追加成功前先把截断与写入推进落盘列表；仿真器有自研随机源、乱序网络和崩溃重启，检查器带一套独立于协议的顺序模型，违例报告会把卡住的时刻和放不进去的操作区间打印出来。它在仿真里还查出过真问题：零故障却选不出主，它没有乱调超时参数，而是缩到最小场景，查出定时器每次重置都新增事件却从不取消旧的；另一处是某个种子下分区节点返回旧值，据此找出读一致性只在任期开始确认一次领导权的缺陷。

A 做得不好的地方也很清楚：一个用例都没有，题面要求的大规模种子回归无从认定，检查器还把预算耗尽当成已证实的违例，接手的人得先把测试补上，才敢采信它跑出来的那些结论。但这是能继续往下收敛的半成品，接口设计写得再准也替代不了实现，所以 A 更好。

## 24

两边的病因找得一样准：other() 认自定义属性时拿的是还没处理过的首个 word token，而 decl() 早把开头的星号或下划线挪进了 raws.before，于是输出端当它是自定义属性，解析端却按普通声明把结尾的注释截掉。改法也等价，A 抽了个具名辅助函数，还写注释点明与 decl() 的耦合，比 B 的正则好读一点。所以能看出谁做得更好的，是题面那两条硬要求有没有落进测试。

A 在 test/stringify.test.ts 里用三层循环把前缀、属性名和结尾形态排了一遍，往返这条查得密，但题面要的两条没人看住：插件改过值之后输出对不对，程序化追加注释时还要不要补分号。这两条恰恰是那套启发式规则存在的理由，将来谁动了 other() 把它们弄坏，测试不会响，只能等下游插件报上来才知道，到那时还得回头把这两条用例补齐。B 把两条都写成了用例，前缀集合更宽，还分别覆盖根层文件末尾和后面跟着兄弟声明两种情形，又顺着 tokenize.js 里 word 的边界说清了为什么只有这两个字符会两端不一致。

A 的过程还绕了一段：没用仓库在用的包管理器，装到的夹具版本和锁文件对不上，为这个并不存在的故障花掉不少工夫，最后集成和覆盖率都没顾上。辅助函数带来的那点可读性优势抵不过缺掉的这两条测试，这么看下来 B 更好。

## 26

两边都定位到 lib/transform.js 里 AST_DynamicImport 没注册 descend，补法也一样，能看出谁做得更好的是遍历打开以后的连带影响。

B 抓到两处 A 完全没碰的地方，关键是 lib/output.js 那处。序列表达式要不要加括号，父节点判定只认调用节点，于是动态引入里的逗号表达式被打印成两个实参，而第二个实参是选项位置，跑出来的行为和原代码不一样了。这不是可有可无的细节：序列合并一类优化能把序列搬进参数，恰恰是这次把遍历打开之后才发生的事。另一处是把动态引入补进 reduce-vars 的逃逸边界，让它和普通调用参数一样保守。它还用回退修复的办法确认新增用例不是空转，改强了其中过松的一条。

A 的长处是结论可核验，写脚本把节点继承关系和注册表交叉比对，排掉空实现造成的误判，确认只有动态引入缺注册，两套用例和静态检查都通过。差的地方是它只验证了修复本身有没有生效，没有往下追遍历打开后新出现的影响，lib/output.js 那处就是这么漏掉的。B 的问题在交付：改完那两处之后没有再跑完整回归，风险没复核就交了。不过漏跑回归留下的是未知，打印出行为不一致的代码是拿到产物的人直接会撞上的，得把动态引入也算进那处括号判定才能修好，这么看下来 B 更好。

## 33

题面把「不能把原本能通过的声明改成报错」写成了硬约束，A 恰恰撞在这条上。它新增的 lexer-math-check.js 里，line-height 上百分比减长度、opacity 里数值加百分号，用例核对的都是必须报错；可前者的语法本就是 length-percentage，后者的百分号等价于数，浏览器两种都收，等于把合法写法定成错误，还用测试固定下来。后面谁动 calc 这块代码，都得先把这几条反向的期望逐条改回去才能用。

这套用例还一次都没跑过：支撑它的 host 闭包推断先被通配生产式吞掉单位类别，策略推翻重写，等 checkMathExpressions 改完签名重新挂回 Lexer，套件就再没跑起来。

B 把推导放进 generic.js 的 math 匹配器，另起 lib/lexer/calc.js 做递归下降和维度合并，百分比允不允许交给属性匹配时的探针：含百分号的整段表达式换成一个百分号 token 再匹配一次，让属性语法自己给结论，border-width 被拦下，width 和 opacity 照旧通过。它差在错误靠模块级槽位传回 Lexer，是隐式的全局状态。A 在报错定位粒度上更细，但这点好处架在反复返工的推断之上，B 有改前改后的对拍和全量回归兜底。这么看下来 B 更好。

## 35

B 的大小写探测在做法上比 A 更合理一些：不看 process.platform，而是翻转路径里字母的大小写之后比较 lstatSync 的 ino，探测出错就退回区分大小写，失败即收紧。可惜这段最精巧的代码一行测试都没有，为了让仓库的行覆盖门槛过关，B 反复改写 c8 ignore 的形态与范围，最后连 Linux 上本来可达的那个返回分支也圈进了忽略块，等于用抑制代替测试。这是一条安全修复，探测逻辑既没被执行过，又被排除在覆盖统计之外，日后哪个平台上探错了也没有用例会发现，接手的人得先拆掉忽略块补上真跑的用例。

A 的改法窄。lib/previous-map.js 里加了 realpathOr 与 isInsideDir，loadFile 先把 CSS 文件所在目录和 map 路径各自解析成真实位置，任一失败就当作不可读。test/previous-map.test.ts 覆盖了指向目录外的链接、断链、互指成环、中间段逃逸，整段新代码不靠忽略就达到了覆盖要求。A 的短板是大小写判断按平台名近似：Linux 挂载不区分大小写的卷时会漏判，APFS 格式化成区分大小写时又会把仅大小写不同的两个目录当成同一个。

比起平台名近似带来的偶发误判，未经执行又被排除出统计的探测代码代价更高，所以 A 更好。
