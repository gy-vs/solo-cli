# Solo CLI · 指挥中心

把「设计题目 → 领题排队 → Docker 跑 Claude Code → 判定 → Cursor 五维分析 → solo-qa 质检 → 上传」串成一条可视化流水线，支持多题并发，一题一容器。

并发额度按容器算，超出的排队，一个容器退出立刻有下一个补上；两侧都跑完自动提交产物、自动分析、自动质检，不需要人工点确认。

## 一键启动

```bash
cp .env.example .env        # 至少确认 CODER_ROOT 指向宿主机上的 solo-coder 目录
docker compose up --build   # 首次约 3–5 分钟（拉取 docker CLI、安装 Cursor CLI、构建前端）
```

启动成功后后端日志会打印：

```
Startup Success
Console : http://localhost:8788
API     : http://localhost:8788/api/health
```

浏览器打开 <http://localhost:8788>。

## 首次配置（设置页）

| 分组 | 必填项 | 说明 |
|---|---|---|
| solo-qa 身份 | `solo_qa_session`、`solo_qa_csrf` | 从已登录浏览器的 Cookie 复制；「测试 solo-qa 身份」应显示登录用户 |
| Claude Code 容器 | 网关 Key | 注入容器的 `apikey`；镜像默认 `adminfather/benzhi-claude-code:20260915-mount`，这个 tag 没推到 Hub，本机没有就 `docker build -t adminfather/benzhi-claude-code:20260915-mount cc-image` 重建 |
| Cursor CLI 分析 | Cursor API Key、模型 | Key 在 cursor.com/dashboard/api 创建；「测试 Cursor」返回 `pong` 即可 |
| 调度 | 并发数、超时、暂停出队 | 默认 3 并发、单题 120 分钟 |
| 自动流水线 | 销毁 / 分析 / 质检三个开关 | 默认全开；分析与质检共用并发额度，默认 2 |
| 守护 | 巡检间隔、重跑与超时上限、暂停异常处理 | 默认 300 秒一轮、3 次 / 2 次；模型停机前打开「暂停异常处理」，见下文 |
| solo-qa 质检 | 项目路径、镜像 | 复用 solo-qa 自己的后端镜像，只读挂载它的源码与 `.env`；「测试质检通道」会连一次远程库 |
| 题目设计 | GitHub Token | 出题要建仓库、推快照；本机执行 `gh auth token` 取值 |
| 跨设备题库 | 启用开关、仓库、本机标识、字面阈值 | 多台设备共享题库与领取归属，同时用于互相查重；单设备可关。仓库须为私有（里面存题面全文），本机标识必填且两台不能重名 |

所有值 Fernet 加密存于 `./data`，界面只回显密钥末 4 位。`.env` 中的 `CURSOR_API_KEY` 等仅作首次种子。

密钥在界面上显示为掩码（`••••••••` + 末 4 位），保存时不会回传，留空也不会清掉已存的值；要换值就直接覆盖输入。加密密钥 `secret.key` 和库一样在挂载的 `./data` 下，重建镜像、`docker compose down` 都不会丢配置。写入时只要值里出现掩码字符就一律拒绝，避免「保存全部」把掩码当真值覆盖掉密钥；每次写入与跳过都记在后端日志里（只记项目名不记值），配置真出问题时能追溯。启动时还会体检一次，发现库里存的是掩码就清空并在日志里点名。

## 目录约定（CODER_ROOT 下）

```
prompt.md            题库：多题，每题以「题号：NN」起头，正文位于「以下为发送给模型的 prompt 正文」之后
workspace/NN/        初始快照 git 仓库，挂为容器 /workspace（门禁要求 HEAD == 快照 SHA 且干净）
出题/轨迹/NN/         容器 ~/.claude/projects 挂载点，启动前必须为空，结束后含一份 <sessionId>.jsonl
出题/分析/NN/         产物副本 repo/、trace_index.json、analysis_prompt.md、agent 原始输出
出题/prompts/NN.md   可选归档，回填 SessionID / TurnID 时一并更新
```

## 单题流程

1. **题库** → 「领取并启动」：先把工作区切到这道题的分支（默认 `q` + 题号，设置里可改模板），再做门禁检查（Key、镜像、容器名、题目分支、HEAD、干净、黑名单泄漏扫描、轨迹目录空、同项目是否有题在跑）。阻断项可一键「切到题目分支」「重置到快照」「归档轨迹」「删除残留容器」。并发满了就进队列。
2. **运行舱**：`docker run -i … print < prompt`，只把 prompt 正文送进 stdin；stream-json 事件实时落库并通过 SSE 推到事件流。超时自动 `docker stop`。思考 token 那种一秒几百条的心跳不落库，只按 2 秒推一条进度；事件流默认回放最后 600 条，完整过程看轨迹 jsonl。
3. **判定**：进程层（退出码）/ 协议层（`result.subtype`）/ 产物层（轨迹、git 改动）→ `FINISHED | FAILED | TIMEOUT | INTERRUPTED`。后端重启后接管的容器读不到 stdout，拿不到 `result`，这时退出码 0 且本轮有轨迹就按正常结束算，轮次与用量留空并在判定备注里说明；导出轨迹到 `data/exports/NN/`，把 SessionID、TurnID/PromptID 写回 `prompt.md`（原文件另存 `.bak`，只改两行）。只认本轮开始之后写过的 jsonl，上一轮留在目录里的不会被当成这次的结果。
4. **自动流水线**：轨迹导出成功后销毁容器 → 跑五维分析 → 跑质检。没产出轨迹时保留容器并跳过分析，原因写在题目卡上。
5. **五维评审**：在产物副本上运行 `agent -p --model claude-opus-5-thinking-high`，产出分数、第一人称口语描述、证据（步骤号/文件/引文）、需求覆盖表。后端交叉核验：证据能否在轨迹中定位、分数与覆盖是否自洽、描述是否含表情/markdown/结构词。红项禁止上传，黄项人工确认；描述可直接编辑后「保存评审并核验」。

   描述只写现象，位置一律用文件名、函数名、命令来指。**不许用「第 38 步」「第 19、20 步」这类步数说法**（步号只填进 evidence，正文里的残留会在落库前自动剥掉，核验再报红兜底），**第一句必须落在具体东西上**，「我把需求逐条对了产物」「推进顺序我认可」「几个关键判断都做对了」这种总评开头一律红项；第一句夹了评价用词但点到了文件或命令的，只给黄项提醒。

   描述会原样交付给评审方，所以另有两类内容被卡死：**本机路径**（产物副本与 `/workspace` 前缀落库前就剥成仓库内相对路径，其他绝对路径整条压掉，核验再对宿主路径报红兜底）和**对核验环境的自述**（有没有装依赖、有没有 node_modules、跑不跑得起来、「产物副本」「我这边」一律红项）。命令跑不了就只依据代码与轨迹下结论，不写为什么没跑。
6. **质检**：调 solo-qa 的质检链路跑硬校验、查重、模型描述判定，只取结论，不写它的库、不碰飞书。未通过的项会指出缺什么、原文哪句有问题、该怎么改。
7. **上传**：`form-schema → /submissions/upload → /submissions` 两步上传；422 逐字段回显，401 提示更新 Cookie。`harness_version` 以轨迹里的版本为准（和镜像实测值不一致时以轨迹为准，否则质检直接打回）。上传成功后把工作区改动提交到这道题的分支（`git add -A` + commit，带 SessionID / TurnID / 初始快照，不 push），提交信息回显在上传页；工作区处于游离 HEAD 或落在别的分支时不提交，直接把原因报出来。不想自动提交就关掉设置里的「上传后提交工作区代码」。
8. **完成并销毁**：容器通常已被流水线销毁；手动点击可再次确认并标记 `DONE`。

## 本机启动项目与录屏（宿主机代理）

分析出结论后，题会停在「待录屏上传」等人录一段。这一步的两个动作——把项目在本机跑起来、录屏——后端都干不了：它在 Linux 容器里，工作目录虽然挂进去了，在那儿执行命令用的却是容器自己的 Node/Python，屏幕上也不会有终端窗口；屏幕录制更是 macOS 按「发起进程所属 App」授权的系统权限，容器拿不到。所以这两件事交给一个跑在宿主机上的小代理。

```bash
open host-agent/启动宿主机代理.command    # 或 python3 host-agent/solo_host_agent.py
```

它只用 Python 标准库，不装任何依赖；窗口留着别关。首次启动会在 `data/host-agent/token` 生成口令，后端通过挂载的 `/data` 自己读，不用配。第一次点录屏若报「一帧都录不到」，去「系统设置 → 隐私与安全性 → 屏幕录制」把「终端」勾上，回到代理窗口 Ctrl+C 重跑一次。

### 先看这一侧该录什么

录屏卡人的从来不是工具，是「这玩意儿到底该录什么」。所以每一侧都会先探一下形态，就挂在按钮旁边，点「怎么录」展开：

| 形态 | 判定依据 | 录屏的重头戏 |
|---|---|---|
| 全栈 | 前后端框架都在，或 monorepo 里前后端子项目都有 | 从界面走完整条链路，顺带把后端日志或网络面板带一眼 |
| 纯前端 | 有 React / Vue / Vite 这类框架，或根上摆着 index.html | 开浏览器走一遍改动涉及的交互，边界状态也点到 |
| 纯后端 | 有 Express / Django / FastAPI / Spring 这类服务端框架 | 把改动涉及的接口打出来看响应，正常和异常入参各一次 |
| 无界面 | 认出了技术栈但没有任何界面或服务信号，就是库或 CLI | 没有界面可看，同一段输入跑出改动前后的行为差异就是效果本身 |

判定只看依赖清单和目录结构这类确定性证据，依据会列出来给你复核；认不出来就直说认不出来，由你按 GSB 的启动说明拿主意——猜错形态比不猜更耽误事。

无界面项目还会把 GSB 那串启动命令按用途拆到三个环节里：跑复现/演示的一行式脚本、点名跑的那几条用例、完整测试套件。每条命令都能一键复制。这三段在录屏里是不同的镜头，混在一起录出来就没有重点了。

### 两个按钮

代理起来后，题库的「待录屏上传」每张卡片、运行舱「已结束」列表的对应行、以及详情页的录屏页签上，都会出现两个按钮：

- **启动项目**：在 Terminal.app 开一个新窗口 `cd` 到 `workspace/<题号>/<侧>`，把 GSB 启动说明里装依赖那几条（`npm ci`、`pip install`、`python -m venv` 等）直接跑掉，其余命令倒序塞进这个窗口的历史，按 ↑ 就是第一条，录屏时自己掌握节奏。跑出来的东西要是监听了端口，界面上会把 `http://localhost:端口` 显示成可点链接——只认这个终端会话的后代进程，机器上别的服务不会混进来。
- **录屏 720p**：ffmpeg 录屏，高度锁 720、宽度按屏幕比例取偶数（不拉变形），文件落在 `reports/<题号>/`。多屏时可以选录哪块。停录后路径自动填进「本机文件路径」，点「上传」就换回链接。

没装 ffmpeg 的话 `brew install ffmpeg`。代理没起来时按钮会按灰并说明怎么起。

## 进容器看现场

详情页的「终端」是一个真终端：后端在容器里 `docker exec -it` 开一个 shell，接到浏览器上的 xterm，能敲命令、有颜色和光标，`git status`、`git diff`、`vim`、`top` 都照常用。题跑着的时候，这是唯一能确认「模型此刻把工作区改成了什么样」的办法——那份账要等收尾才记得上。

同一个抽屉里的「日志」是 `docker logs -f` 的原样回放，只能看。它跟事件流的分工在于：事件流是解析、过滤、落库之后的结果，噪声事件被丢掉了，采集一断就什么都没有；日志是容器此刻真正往外写的每一行，判断「还在不在动」只能看它。

题还在跑时请只读不写——终端里的改动会连着进这道题的产物和 git 改动统计。浏览器一关，容器里那个 shell 连同它起的子进程都会被收掉，不会留在里面继续跑。容器已经销毁或已经退出时终端开不了，会直接说明是哪一种。

## 队列

排队和并发额度的单位都是**容器**，不是题。一道 GSB 题要跑 A、B 两侧，两侧各占一个槽、各排各的队：谁排到谁先出闸，跑完的结果在库里等着对方，两侧都齐了巡检自动推产物、开对比分析。所以空出一个槽就一定有一个容器补上去，不会出现「只剩一个槽、队头那道题却要两个」而让机器闲着。

「队列」页按容器列出在跑的和排队的，排在第几个、是第一次跑还是被退回来重跑、已经跑了多少分钟都直接写在行上；可以置顶 / 上移 / 下移 / 废弃，也能在线改容器上限、暂停出队（暂停只影响新容器出闸，已在跑的不受影响）。顶部的「心跳」是调度与巡检两个后台循环的存活证据，它们停了会直接在页面上报警而不是安静地不干活。

## 异常重跑与自动废弃

跑坏的那一侧由巡检自动重跑，动作是完全回退：销毁容器、归档轨迹、把工作区从主干在初始快照上重建，再排回队列。判的是「过程坏了」而不是「模型做得不好」——容器内 Claude Code 自带的十次网关重试期间不介入，重试用尽仍没跑成才算一次。

两个上限分开数，先撞到哪个按哪个来，用尽后**整道题自动废弃**而不是挂起等人：

| 上限 | 默认 | 为什么 |
|---|---|---|
| `watchdog.max_retries` | 3 次 | 一侧跑满三次还不成，多半不是偶发 |
| `watchdog.max_timeouts` | 2 次 | 一次超时要烧掉整个运行超时，容忍度更低 |

废弃会把另一侧还在跑的容器一并停掉——GSB 交的是两侧对比，一侧修不好，另一侧跑得再好也交不上去，让它继续占槽位只是拿机器时间换一份用不上的结果。题留在题库「已废弃」标签页，按「恢复」就能捞回来，轨迹和产物都还在磁盘上。

**模型或网关要停机时，先在队列页打开「暂停异常处理」**（`watchdog.paused`）。停机期间每一侧都会跑挂，而重跑的动作是把工作区连 `.git` 一起删掉重建，不暂停就会把一整批题清空、再跑满次数整题废弃，可它们缺的只是一次能连上模型的重跑。开关打开后判定照做、异常照记（队列页「看护记录」里标成「挂起 · 未重跑」），但不重跑也不废弃，工作区、轨迹、容器一概不动；运行中的容器不受影响，两侧都跑成的题照常配对分析，人工点「重跑」「废弃」仍然有效。关掉开关，挂着的那些侧会照常按记下的原因重跑。

## 设计题目

「设计题目」页输入数量后，Cursor CLI 以 `/solo-prompt` 调起 `~/.cursor/skills/solo-prompt`，由那份 skill 完成选题与 prompt 正文；仓库落地、题面渲染、写盘、推远端题库、导入、查重由本地代码接手。**出题规则只有 skill 这一份**，难度档位、配比、任务类型、查重与配额都改在 skill 里，本项目不留副本——两份规则必然漂移，而漂移不报错，只会安静地出一批不合规的题。

skill 目录按 `SKILL_DIR` 挂进后端容器，再链到 CLI 认的 `~/.cursor/skills`。链不上时出题直接失败而不是降级：CLI 找不到 skill 不会报错，只会把 `/solo-prompt` 当普通文本，模型照字面猜一套规则出题，事后无从分辨。

skill 的 Phase 1 要求实测容器能力，而出题时 CLI 跑在只读模式下起不了容器，所以这一步由后端代为实测（命令清单与外网可达性），结论作为事实交给 skill 约束选题。Phase 4.4 的判定点不写进题面，改为随设计记录输出到运行日志。

产出导入题库后跑两层查重：solo-qa 的规则 A（字面/近字面）与规则 C（同仓库语义雷同，含同批互查），查的是**已提交到平台**的历史数据；命中的直接废弃并记下原因。查重本身没跑成时不会放行，题会留在库里并标注，人工决定。

出题需要后端容器里的 `gh` 与 GitHub Token，还需要工作区里有 `drafts/brief.md`（skill 的 Phase 0 读它取当期口径）；页面顶部的前置检查会逐项标出缺什么。

绕开控制台、直接在 Cursor 里敲 `/solo-prompt` 出的题不会自动进题库：控制台只认远端题库，不扫 `drafts/`。skill 的 Phase 6 末尾会调 `POST /api/design/pool/bootstrap` 把本机 `drafts/` 下的题推上去，接口幂等（已在远端的跳过），漏了事后补调即可。

## 跨设备题库

一个 GitHub 私有仓库同时当**题库**和**查重池**：所有设备出的题都推上去，领题从那里拉，谁领了哪道题也记在上面。设置页填三项：启用开关、仓库（`owner/repo`，不存在会自动建成 private）、本机标识（必填，两台设备不能重名）。关掉就回到单设备模式，题库只认本机的题面文件。

仓库里三样东西：

```
pool.jsonl           一题一行，存题面全文（draft）、prompt 正文、基底、快照
claims.jsonl         一次领取或释放一行，记 entry_id / 设备 / 动作 / 时间
prompts/<设备>/NN.md 题面的可读副本，纯粹为了能在 GitHub 上直接打开来看
```

**题库来源**。启用后远端是唯一真相源，启动时和点「同步远端题库」时各拉一次，把没被领走的题投影成本机待领取的题。本机 `drafts/` 里的题面只是出题的产物，不再被重复导入——两个来源并存会让同一道题在本机多出一行没有远端归属、因而不受独占保护的副本。别的设备出的题，题号会加设备后缀（`01` → `01-mac-air`）：题号是工作区目录名和容器名的一部分，两台设备都从 01 开始编号，不区分就会让两道不同的题共用一个工作区。

**领取归属**。远端只回答「这道题归谁」，做到哪一步由各自本机说了算。点「领取并启动」时先去远端占位，成功了才 clone 分支、跑门禁——准备工作区要几十秒到几分钟，等跑完再发现题没了，这段机器时间就白烧了。题被别的设备领走时会提示一句并立刻把它从本机题库里撤掉，页面自动刷新。点「放回」会撤销远端的登记，让别的设备能领；做完和废弃都不撤销，题保持归本机。

**并发怎么保证不重领**。git 没有 compare-and-swap，独占是三步凑出来的：拉最新看有没有主 → 写一行 claim 并推 → **推完再拉一次重新核对**。第三步不能省：`merge=union` 会把两台设备的 claim 都留下，谁赢由行里的时间戳判而不是由谁先 push 判，少了这一下两边都会看到自己成功然后双双开工。推不上去就把本地那行抹掉，这次领取整个不算数。仲裁规则（先 claim 的赢、release 只认本人发的）只依赖文件内容不依赖行序，所以两台设备读同一份文件必然算出同一个归属，不需要中心仲裁。

**查重**。出题前把全池投影成 `drafts/index.md`——skill 的 Phase 3 本来就读这个索引做功能点查重与按基底的配额统计，于是跨设备的语义查重由设计阶段顺带完成；另一台设备的题在表里标成 `07@设备名`。落地前再做一次确定性的字面查重兜底，同时比池内与同批候选，阈值默认 0.45（实测同一道题换措辞在 0.5 上下，同基底的不同功能点在 0.3 上下）。

两个 jsonl 都是 append-only 并且配了 `merge=union`，两台设备同时各加几行不会产生需要人工解决的冲突。Token 不写进 remote，每次 fetch / push 现拼带凭据的 URL。目录在 `./data/pool`，不在工作区下——那边的 `workspace/` 会挂进容器，这些文件绝不能进容器可见范围。

题面全文是后加的字段，早于它入池的题只有 prompt 正文，缺仓库地址和初始快照，在别的设备上领不了，题库页会点出来还有几道。出这些题的那台设备同步一次就会自动补齐。

## 换一台设备部署

仓库里只有代码。`data/`（库、`secret.key`、导出轨迹、题库的本地副本）和 `.env` 都不进版本库，两台设备各自持有一份，互不覆盖；跨设备共享的只有题库那一个仓库。

拉下来之后照抄 `.env.example` 建 `.env`，把四个宿主路径改成这台机器上的真实值：`SOLO_CLI_ROOT`（本项目）、`CODER_ROOT`（工作区）、`QA_PROJECT_HOST`（solo-qa）、`SKILL_DIR`。前两个必须改——compose 里它们的默认值是另一台机器的绝对路径，而 `docker -v` 的源路径由宿主 daemon 解析，指到不存在的目录时容器照常起来，直到质检挂载轨迹那一步才失败。设置页的密钥要重新填一遍（加密存在各自的 `data/` 下）。

**本项目放在哪里都行，除了 `CODER_ROOT` 里面。** 容器只挂 `workspace/<题号>/<侧>` 与 `sessions/<题号>/<侧>` 两棵子树，把本项目 clone 到其中任何一棵下面，题库、判定点和题面全文就随题目一起交到模型手上了，而界面上看不出任何异常。出题页的「出题资料隔离」检查会挡住这种配法，它属于阻塞项。

出题规则不在这个仓库里，在 `~/.cursor/skills/solo-prompt`。**两台设备都要配跨设备题库**，哪怕只有一台出题：题库和领取归属都在那个仓库里，不配的设备既拉不到题，领取也不受独占保护。本机标识两台必须不同。

后端重启不会打断容器里正在跑的题：启动时按容器实际状态重新接管，结束后照常收尾。分析与质检是后端进程内的活，重启会中断，启动时会把卡在「分析中/质检中」的题复位并自动重新排进流水线。

题库按状态分了八个标签页（全部 / 待领取 / 已领取未跑 / 排队运行中 / 待评审 / 已评审 / 已上传完成 / 已废弃），点过领取但还没跑的题在「已领取未跑」里。这里的状态全是本机口径；远端只记归属，见上面的「跨设备题库」。

想重跑一道题就点题卡上的「还原」（详情页是「还原到做题前」）：销毁残留容器 → 工作区回到题目分支并 `reset --hard` 回初始快照 commit、`git clean -fdx` → 轨迹目录带时间戳归档 → 删掉导出的轨迹副本与分析中间产物 → `prompt.md` 里回填过的 SessionID 与 TurnID 改回占位 → 清空运行、分析、评审、质检记录与事件。做完这道题回到「待领取」，门禁能直接过。工作区里未提交的改动会被清掉，轨迹是归档不是删除；分支上已有的交付提交在 reset 前会记到 `refs/solo-backup/<分支>-<时间戳>`，用 `git log refs/solo-backup/...` 能找回来。

不想做的题点「废弃」：从题库与运行舱列表中隐藏，在跑的容器一并停掉销毁，轨迹和工作目录仍留在磁盘上；需要时在题库「已废弃」标签页恢复到废弃前的状态。运行中和排队中的题也能直接废弃，不必先停容器——槽位是这里最紧的资源。

每道题的详情页（题卡「详情」按钮）分两种形态：还没跑的题显示提交参数、prompt 全文、项目路径、时间线，左侧可直接执行门禁检查并修复；跑过的题显示事件流、三层判定、五维评审、上传字段与轨迹步骤索引。

## 与 solo-qa 的对接方式

查重和质检都复用 `solo-qa-0908` 自己的后端镜像执行：把 `backend/bridges/*.py` 挂进去，stdin/stdout 传 JSON。这样既拿到它最新的规则实现，又不用把它 pin 死的依赖装进本项目。

桥接只调只读函数（`run_dedup`、`semantic.review`、`qc.runner.evaluate_one`），不写结论、不入查重池、不同步飞书，模型缓存也关掉；待查题目用 `MAX(id)` 之上的虚拟 id，只存在于内存。需要 solo-qa 的 `.env` 能连上它的远程库与模型网关。
